# Плагин WordPress — отправка почты через сервис рассылки

Перехватывает все письма WordPress (`wp_mail`): регистрация, сброс пароля,
уведомления плагинов, формы — и отдаёт их сервису рассылки по HTTP API
вместо `mail()`. Сервис отвечает за очередь, повторы, DKIM, историю отправки
и веб-панель.

## Требования

- WordPress 5.7+ (перехват через фильтр `pre_wp_mail`), PHP 7.0+.
- Работающий сервис рассылки и API-ключ проекта.

## Установка

Скопировать каталог `mailerservice` в `wp-content/plugins/`:

```bash
cp -r integrations/wordpress/mailerservice /var/www/wp-site/wp-content/plugins/
```

или загрузить каталог в архив и поставить через «Плагины → Добавить новый →
Загрузить плагин» — имя каталога внутри архива должно остаться `mailerservice`.
После этого включить плагин в списке плагинов.

## Настройка

Ключ проекта выдаётся на стороне сервиса:

```bash
php bin/mailer key:create wordpress
```

Дальше в админке WordPress: **Параметры → Сервис рассылки**:

| Настройка     | Что означает                                                            |
|---------------|-------------------------------------------------------------------------|
| `url`         | адрес сервиса, например `http://mail.internal` (без `/api/v1`)          |
| `apikey`      | API-ключ проекта                                                        |
| `mode`        | `queue` — отдать письмо в очередь и не ждать; `sync` — дождаться отправки |
| `transport`   | имя транспорта, если нужен конкретный; пусто — транспорт по умолчанию   |
| `tag`         | метка писем в панели сервиса, по умолчанию `wordpress`                   |
| `from_email`  | отправитель всех писем; пусто — из заголовка `From` или транспорт сервиса |
| `from_name`   | имя отправителя (необязательно)                                          |
| `timeout`     | таймаут запроса к сервису, секунд                                       |
| `fallback`    | если сервис недоступен — отправить письмо штатными средствами WordPress  |
| `logging`     | журнал диагностики (последние 50 событий, раздел ниже)                   |

Пока не заполнены `url` и `apikey`, плагин не вмешивается: почта уходит как
раньше.

`from_email` должен быть разрешён транспорту сервиса. Яндекс шлёт только со
своих адресов: письмо с чужим `From` упадёт на отправке с ошибкой
`550 5.7.0 Sender address rejected: not owned by authorized user`. Если
`from_email` не задан и в письме нет заголовка `From`, поле `from` в запрос
не передаётся — отправителя подставляет транспорт сервиса, и такие письма
не отклоняются.

## Проверка

**Параметры → Сервис рассылки**:

- «Проверить» — проверка ключа (`/api/v1/messages`) и запрос `/api/v1/health`:
  база, очередь, воркер;
- тестовое письмо — уходит обычным путём WordPress (`wp_mail`), то есть
  проверяет всю цепочку вместе с плагином;
- **Отправитель (Email/Имя)** — адрес, от которого уходят все письма. Должен
  быть разрешён транспорту сервиса: SMTP Яндекса отклоняет письмо с чужим
  адресом («550 5.7.0 Sender address rejected: not owned by authorized user»).
  Пусто — берётся заголовок From письма, а если его нет, отправителя
  подставляет транспорт сервиса.

Отправленные письма видны в панели сервиса с меткой `wordpress`; в `meta`
попадают название сайта, его адрес и логин пользователя, от чьего действия
ушло письмо.

## Диагностика

На странице настроек есть раздел **Диагностика**:

- версия WordPress и PHP, наличие cURL, состояние `wp_mail` — переопределена
  ли она другим плагином;
- список активных плагинов и перехватчиков почты (`pre_wp_mail`,
  `phpmailer_init`) с их приоритетами — видно, кто ещё вмешивается в отправку;
- журнал событий: что плагин делает с каждым письмом — передан ли он сервису,
  какой ответ и идентификатор вернул сервис, ошибки, включился ли `fallback`.

Журнал хранит последние 50 записей в опции `mailerservice_log` и доступен без
доступа к логу сервера. Если журнал пуст, фильтр `pre_wp_mail` не срабатывает
вообще: проверьте версию WordPress (нужна 5.7+) и другие почтовые плагины.
Журнал включается/выключается настройкой «Журнал диагностики».

## Режим `sync`

По умолчанию (`queue`) сайт получает ответ сразу после постановки письма в
очередь — страница не ждёт SMTP. Режим `sync` заставляет сервис отправить
письмо немедленно и вернуть результат: `wp_mail` вернёт честный результат, но
действие пользователя будет ждать почтовый сервер. Для обычного сайта
разумнее `queue`.

В этом режиме письмо, которое сервис принял, но не смог отправить, — не то же
самое, что непринятое: оно есть в панели со статусом `failed`, и его можно
повторить оттуда. В журнале диагностики будет причина от почтового сервера
и идентификатор письма, а не «сервис ответил кодом 502».

## Что делать, если сервис лёг

При `fallback = вкл` (по умолчанию) плагин отдаёт письмо обычной отправке
WordPress, а ошибку пишет в журнал сервера (`error_log`). Выключенный `fallback`
означает «либо через сервис, либо никак» — `wp_mail` вернёт `false`.

## Как устроено

Плагин подписан на фильтр `pre_wp_mail` (WordPress 5.7+), который срабатывает
до сборки письма в PHPMailer:

1. `includes/class-mailer.php` — разбирает аргументы `wp_mail` (получатели,
   тема, тело, заголовки, вложения) так же, как это делает сама `wp_mail`,
   собирает запрос к API; при успехе возвращает `true` и отменяет штатную
   отправку. Заголовки `From`, `Cc`, `Bcc`, `Reply-To`, `Content-Type`
   превращаются в поля запроса, остальные уходят как дополнительные заголовки.
2. `includes/class-api.php` — клиент API: `POST /api/v1/messages`, разбор
   ошибок, `GET /api/v1/health`. Запросы идут через `wp_remote_request` —
   с учётом прокси и HTTP-транспорта WordPress.
3. `includes/class-admin.php` — страница настроек.

Письмо собирает сам сервис, поэтому плагины, которые донастраивают письмо на
этапе `phpmailer_init`, на отправку через сервис не влияют.

Отправитель письма: настройка `from_email` → заголовок `From` письма → ничего
(поле `from` в запросе не передаётся, отправителя подставляет транспорт
сервиса). Плагин намеренно не подставляет `wordpress@домен-сайта` — этот адрес
SMTP-транспорту обычно не принадлежит.

Плагин не сможет перехватить почту, если `wp_mail` переопределена до него —
например, mu-плагином из `wp-content/mu-plugins/`. `wp_mail` объявлена как
pluggable, поэтому переопределившая её функция `function_exists` уже не даст
заменить, а её реализация может не вызывать фильтр `pre_wp_mail`. Такая
ситуация сразу видна в разделе «Диагностика»: «wp_mail переопределена: …».
Решение — отключить или поправить переопределяющий плагин.

Каждое действие с письмом пишется в журнал диагностики и в `error_log`: что
перехвачено, что вернул сервис, ошибки, включился ли `fallback`.
