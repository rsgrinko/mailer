# Нагрузочная проверка

Прогон от 19.08.2026, код на коммите `f12972c`, отдельно — проверка на боевом сервере
после наката индексов. Цель — понять, где сервис упирается при
росте числа писем, и починить найденное.

## Стенд и метод

- Один компьютер: Windows 11, PHP 8.3.19, встроенный сервер `php -S`, база в файле
  `var/loadtest.sqlite` — боевые данные не трогались.
- Нагрузку даёт `tools/loadtest.php`: параллельные запросы через `curl_multi`, замер
  p50/p95, отдельно — замеры внутри процесса, без сети и веб-сервера.
- Транспорт `null`: письма никуда не уходят, меряется сам сервис, а не почтовый сервер.

Что из этого нельзя переносить на продакшен буквально:

- **Встроенный сервер обрабатывает запросы по одному.** Все цифры ниже — это один процесс.
  На боевом nginx + php-fpm параллельность даёт примерно кратный выигрыш по числу воркеров
  fpm; латентность одного запроса при этом остаётся такой же.
- **База в файле рядом с процессом.** Боевая MySQL стоит на 10.10.10.85, и один запрос к
  ней стоит ~1.1 мс только на сеть. Страница, делающая 10 запросов, платит +11 мс сверх
  цифр этого отчёта — поэтому сокращение числа запросов на проде выгоднее, чем здесь.
- Замеры сделаны на письмах примерно одинакового размера (1 КБ, без вложений).

## Как рос отклик с ростом базы

Один процесс, по одному запросу за раз, p50 в миллисекундах. Столбец «50 000 после» —
это уже с правками, описанными ниже.

| Сценарий | 150 писем | 1 000 | 10 000 | 50 000 | 50 000 после |
|----------|-----------|-------|--------|--------|--------------|
| Приём письма (`POST /api/v1/messages`) | 23 | 25 | 22 | 37 | **25** |
| Список писем API (`GET /api/v1/messages`) | 18 | 19 | 90 | 230 | **21** |
| Обзор панели (`/ui/`) | 21 | 24 | 150 | 677 | **43** |
| Список писем в панели (`/ui/messages`) | 22 | 24 | 24 | 54 | **38** |
| Поиск по письмам (`/ui/messages?search=…`) | — | 23 | 54 | 156 | 189 |

Отдельно про обзор: на 50 000 писем p95 был **1.4 секунды** — страница, которую открывают
чаще всего, становилась самой тяжёлой.

## Где именно уходило время

Замер каждого запроса отдельно, база 50 000 писем:

| Запрос | Было | Стало |
|--------|------|-------|
| `stats()` — цифры на обзоре целиком | 328 мс | **12 мс** |
| ↳ «отправлено сегодня» | 189 мс | 0.3 мс |
| ↳ «ошибок сегодня» | 61 мс | 0.2 мс |
| ↳ самое старое письмо в очереди | 62 мс | 0.1 мс |
| `dailyStats(14)` — график за две недели | 409 мс | 47 мс |
| Страница списка со статусом | 4.9 мс | 1.6 мс |
| `COUNT` для пагинации | 24 мс | 2.8 мс |
| Поиск `LIKE '%…%'` | 122 мс | 122 мс |

Причина одна и та же: запросы обзора идут по колонкам, которых не было в индексах
(`sent_at`, `updated_at`, `created_at` вместе со статусом), поэтому база перебирала таблицу
целиком.

## Что сделано

1. **Миграция `0003_message_indexes`** — четыре индекса: `(status, sent_at)`,
   `(status, updated_at)`, `(status, created_at)`, `(created_at, status)`. Это и дало
   основной выигрыш: обзор с 677 до 87 мс, список API с 230 до 21 мс.
2. **Пагинация считает строки без подзапроса.** `Database::page()` оборачивал выборку в
   `SELECT COUNT(*) FROM (…)`, и база материализовала подзапрос целиком. Теперь для обычной
   выборки счётчик строится из тех же условий, а подзапрос остаётся только для группировок,
   `DISTINCT` и объединений — там иначе нельзя.
3. **График на обзоре кэшируется** на `UI_STATS_CACHE` секунд (по умолчанию 30). Считать
   разбивку по дням на каждое обновление страницы незачем: обзор с 87 до 43 мс, p95 —
   с 418 до 48 мс. Ноль в настройке выключает кэш.

## Сколько сервис держит сейчас

Замеры внутри процесса, без веб-сервера — это чистая стоимость работы сервиса:

| Операция | Время | В секунду |
|----------|-------|-----------|
| Приём письма через API | 3.1 мс | ~320 |
| Список писем через API | 3.8 мс | ~265 |
| Проверка `/api/v1/health` | 13.3 мс | ~75 |
| Обзор панели | 26 мс | ~39 |
| Список писем в панели | 35 мс | ~29 |
| Страница «Состояние» | 5.1 мс | ~195 |

Очередь, транспорт `null`:

- приём 500 писем — **361 письмо в секунду** (2.8 мс на письмо);
- отправка тех же 500 воркером — **123 письма в секунду** (8.1 мс на письмо).

Через HTTP на встроенном сервере приём выходит 42 запроса в секунду: 3 мс работает сервис
и ещё ~20 мс тратит сам `php -S`. На nginx + php-fpm этой платы нет, и потолок определяется
числом воркеров fpm: четыре воркера дают порядка 300–400 принятых писем в секунду.

Реальная скорость рассылки упирается не в сервис, а в почтовый сервер: одна отправка через
SMTP Яндекса занимает сотни миллисекунд, плюс действуют его собственные ограничения на
число писем. 123 письма в секунду — это верхняя граница самого воркера, до транспорта.

## Проверка на боевом сервере

Прогон по mail.rsgrinko.ru после наката индексов. Письма шли в отдельный проект
`loadtest` через транспорт типа `null` — наружу не ушло ни одного; после замеров проект,
транспорт и все 1801 письмо удалены, чужие записи не тронуты.

Латентность здесь включает канал до сервера: пустой ответ `/api/v1/health` приходит за
~110 мс, из которых работа сервиса — около 13 мс. Поэтому смотреть надо не на абсолютные
миллисекунды, а на то, что они **не растут** с параллельностью.

| Сценарий | Параллельно | Запросов в секунду | p50 | p95 |
|----------|-------------|--------------------|-----|-----|
| `/api/v1/health` | 1 | 8.7 | 110 мс | 115 мс |
| `/api/v1/health` | 4 | 30.5 | 108 мс | 117 мс |
| `/api/v1/health` | 8 | 48.4 | 113 мс | 723 мс |
| `/api/v1/health` | 16 | 72.9 | 112 мс | 754 мс |
| Приём письма | 1 | 8.5 | 116 мс | 119 мс |
| Приём письма | 4 | 28.8 | 118 мс | 179 мс |
| Приём письма | 8 | 50.3 | 120 мс | 182 мс |
| Приём письма | 16 | **104.9** | 135 мс | 219 мс |
| Список писем API | 4 | 21.8 | 153 мс | 624 мс |

Приём письма стоит серверу примерно 6–10 мс сверх канала, и это не меняется от единицы к
шестнадцати параллельным клиентам — nginx с php-fpm раскладывает запросы по воркерам.
При шестнадцати клиентах сервис принял **105 писем в секунду**; ограничением был уже
канал, а не сервер.

**Очередь.** 1200 писем, залитых через API, воркер разобрал со скоростью **133 письма в
секунду** (пик 140) — от полной очереди до нуля за девять секунд. Это близко к локальному
замеру (123 письма/с) и подтверждает, что MySQL по сети очередь не тормозит.

**Запросы панели на боевой базе** (1850 писем, каждый включает ~1.1 мс до 10.10.10.85):
сводка обзора — 8.8 мс, график за две недели — 3.8 мс, список писем — 2.8 мс, список с
фильтром — 3.9 мс, поиск по теме — 5.3 мс. После нагрузки сервис остался в порядке:
`health` — `ok`, очередь пустая, воркер отвечает.

## Что осталось и когда за это браться

- **Поиск по письмам** (`LIKE '%текст%'`) индексом не ускорить: 190 мс на 50 000 писем и
  дальше линейно. Пока приемлемо; если поиском начнут пользоваться постоянно — нужен
  полнотекстовый индекс (в MySQL — `FULLTEXT` по теме и адресам).
- **Список писем в панели** — 35 мс, из них 6 мс запросы и почти всё остальное — сборка
  тридцати строк шаблона. Ускорять есть смысл только вместе с уменьшением числа колонок.
- **Обзор** — 26 мс, дальше упирается в `countByStatus()` (6 мс) и рендер. Если писем
  станут миллионы, счётчики по статусам придётся держать отдельной таблицей.
- **Чистка старых писем** (`queue:purge`) остаётся главным способом держать базу маленькой:
  все замеры выше показывают, что стоимость страниц растёт вместе с таблицей.

## Как повторить

```bash
# отдельная база, боевую не трогаем
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite php bin/mailer migrate
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite php tools/loadtest.php prepare
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite php tools/loadtest.php fill 50000

# замеры без веб-сервера
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite php tools/loadtest.php queries
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite php tools/loadtest.php kernel
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite php tools/loadtest.php worker 500

# по HTTP: поднять сервис на той же базе и бить по нему
DB_DRIVER=sqlite DB_SQLITE_PATH=$PWD/var/loadtest.sqlite UI_AUTH=false \
    php -S 127.0.0.1:8210 -t public public/index.php &
php tools/loadtest.php http http://127.0.0.1:8210 api-accept 8 200
php tools/loadtest.php http http://127.0.0.1:8210 ui-dashboard 1 40
```
