# Регрессы

Здесь остаются отчёты о больших проверках: что смотрели, что нашли, чем чинили и
как убедились, что не сломали остальное. Замеры скорости живут отдельно — в `LOADTEST.md`.

## Прогон 21.08.2026 — права в панели

Повод: в панели показывались кнопки управления там, где действие всё равно недоступно,
а разделы с раздельными правами «смотреть» и «править» открывались формой ввода даже
тому, кто может только смотреть. По ходу проверки нашлось и то, из-за чего администратор
не видел новых разделов сервиса.

### Что было не так

| Где | Что показывалось лишнего |
|-----|--------------------------|
| Карточка письма | «Отправить сейчас», «Вернуть в очередь», «Отменить», «Удалить», «Написать похожее» — без `messages.send` / `messages.manage` |
| Список писем | блок «Массовые действия» без `messages.manage` |
| Состояние сервиса | весь блок «Обслуживание» (миграции, перезапуск воркера, чистка) без `system.manage` |
| Вебхуки | «Разослать сейчас», «отправить», «удалить» без `webhooks.manage` |
| Проекты, шаблоны | «Создать проект», «Создать шаблон» без `*.manage` |
| Карточка проекта | «Выдать новый ключ», «Отключить проект», «Удалить проект» без `projects.manage` |
| Карточка транспорта | «Проверить подключение» без `transports.test` |
| Обзор | письма, вебхуки и транспорты показывались всем вошедшим, независимо от прав |
| Ссылки в чужие разделы | из карточки письма и списков вели на проект и транспорт даже без прав на них — по нажатию 403 |
| Формы проектов, транспортов, шаблонов | поля ввода и «Сохранить» тому, у кого есть только право на просмотр |
| `UI_ALLOW_ACTIONS=false` | кнопки над письмами оставались, а массовые действия настройку вовсе не проверяли |

Отдельно нашлось главное: **новые разделы не открывались администратору**. Права
встроенной роли лежали в базе списком, записанным при её создании, а список прав в коде
с тех пор вырос. Поэтому «Стоп-лист» и «Журнал действий» не показывались вообще никому:
у роли администратора этих прав в базе не было.

### Что сделано

- Каждое действие в разметке закрыто своим правом: кнопка, форма и ссылка показываются
  только тому, кто может ими воспользоваться (`View::can()`).
- Разделы с раздельными правами («смотреть» и «править») без права на правку показывают
  значения списком, а не полями ввода: контроллер передаёт во вьюху `editable`
  (у транспортов — `readOnly`), разметка значений — общий шаблон `src/Ui/views/props.php`.
- Обзор скрывает блоки, на которые нет прав; если не осталось ни одного — говорит об этом
  прямо, а не показывает пустую страницу.
- Права встроенной роли берутся из кода (`RoleRepository::permissions()`), а не из базы.
  Тем же правилом пользуется `UserRepository`, когда собирает права вошедшего, — иначе
  форма роли показывала бы одно, а доступ работал по другому. Подсчёт «последнего
  управляющего пользователями» тоже учитывает встроенную роль.
- `UI_ALLOW_ACTIONS=false` теперь и прячет кнопки над письмами, и отклоняет массовое
  действие (раньше `bulk()` настройку не смотрел).
- Мелочи вёрстки: галочка с подписью занимает свою строку (`label.inline` стал `flex` —
  раньше несколько коротких слипались в одну строку на странице ролей), а длинное
  служебное значение на странице «Состояние» переносится вместо горизонтального скролла.

### Чем проверено

- **Тесты**: 132 успешно, 1 пропуск (DKIM без `openssl.cnf`). Добавлены проверки в
  `tests/AccessTest.php`: роль «только просмотр» не видит ни одной кнопки правки на
  одиннадцати страницах, владелец с правами видит их все (обратная проверка), обзор
  показывает только разрешённые блоки, `UI_ALLOW_ACTIONS=false` прячет кнопки и отклоняет
  массовое действие, встроенная роль получает новые права и в форме роли, и у вошедшего.
- **Локально в Chrome**: панель на отдельной базе SQLite, две роли (администратор и
  «только просмотр»). Проверены карточки проекта, транспорта, письма, страницы состояния,
  стоп-листа, ролей; сверено, что администратору ничего не спрятали.
- **На боевом сервере** (`mail.rsgrinko.ru`): полный проход по разделам от лица роли
  «Аудитор» (только просмотр) и роли «Пользователь» (свои данные с правкой).

### Что гоняли на боевом сервере

| Проверка | Результат |
|----------|-----------|
| API: приём письма, статус, список, health, отказ без ключа | письмо принято, доставлено воркером через транспорт `log`, без ключа — 401 |
| API: стоп-лист (закрыть адрес, письмо на закрытый адрес, открыть обратно) | письмо получило статус «в стоп-листе», адрес открыт обратно |
| Панель: отправка письма из формы «Написать» | ушло синхронно, `.eml` записан, история и ссылки на месте |
| Панель: письмо упало на выключенном транспорте и было возвращено кнопкой | принято → ошибка → повтор из панели → попытка №2 → отправлено |
| Панель под ролью «Аудитор» | ни одной кнопки правки на 11 страницах, «Написать» — 403 |
| Панель под ролью «Пользователь» | все кнопки на месте, закрытые разделы — 403 |
| Разделы «Стоп-лист» и «Журнал» у администратора | появились после правки прав встроенной роли |
| Страница «Состояние», страница ролей | горизонтального скролла нет, галочки по строкам |

Данные для проверки заводились свои и удалены после неё: проект, транспорт (`log`,
не основной), шаблон, временный пользователь и четыре письма. Счётчики таблиц сверялись
до и после — сошлись все, кроме `audit_log`: записи журнала о входах и действиях
регресса оставлены намеренно, стирать историю нельзя.

### Добор 21.08.2026 — роли и заведение администратора

По итогам прогона на боевом сервере проставлены права ролям, заведённым до появления
новых разделов (сами данные ролей не пересобирались, только добавлены недостающие коды):

| Роль | Было | Стало | Добавлено |
|------|------|-------|-----------|
| Аудитор (только просмотр) | 8 | 10 | `suppressions.view`, `audit.view` |
| Пользователь (свои данные) | 11 | 13 | `suppressions.view`, `suppressions.manage` |
| Администратор (встроенная) | 18 в базе | 21 из кода | новые права приходят сами |

Заодно проверено, что администратор заводится с полным набором прав всеми тремя путями:
страница первого запуска `/ui/setup`, `php bin/mailer user:create --role=…` и форма
пользователя в панели — везде 21 право из 21 и доступ к чужим данным.

Роль администратора теперь ищется по признаку `is_system`, а не по имени: имя роли
меняется в панели, и поиск по строке оставил бы первого пользователя вовсе без прав.
Если встроенной роли в базе нет, страница первого запуска её заводит (`ensureAdmin()`).

Раздел «Роли» на чистой установке показывает две роли — «Администратор» (21 из 21,
плашка «встроенная», без кнопки удаления) и «Пользователь» (13 из 21). Тест
`каждое право попадает в форму роли` следит, чтобы новое право не осталось без подписи
в `Permission::GROUPS`: иначе его не было бы видно в форме и выдать его было бы нечем.

### На что обратить внимание

Администратору новое право достаётся само, а прочим ролям его нужно проставить руками
в `/ui/roles` — иначе люди просто не увидят новый пункт меню. Сверить роль с полным
списком прав: `php bin/mailer role:list <название>`.
